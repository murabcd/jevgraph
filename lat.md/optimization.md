# Context and cost optimization

Model routing requires reviewed quality and latency evidence, then compares complete-turn cost per passing answer. Preparation can require projected savings to cover its cost. See [[context]], [[routing]], and [[chat]].

Convex stores reusable summaries through [[persistence]]. Provider calls use direct AI SDK packages. Retrieval embedding and Jev reranking are distinct ledger purposes, with published embedding rates in [[src/lib/model-pricing.ts]]; failed attempts and unknown usage retain the existing accounting rules. Retrieval does not prove a provider-cache hit.

## Model planning

Planning contracts validate model choices and separate forecasts from actual usage.

[[src/lib/model-routing.ts]] owns evaluation and automatic modes, answer criteria, minimum distinct cases, pass-rate and full-turn p95 latency limits, expected output/reuse, and validated plans. Evaluation mode runs the explicitly selected allowed model and reasoning pair. [[src/lib/model-configuration.ts]] owns supported pairs and their model@effort identity; [[src/lib/model-routing.ts]] limits each node to sixteen unique configurations with explicit task criteria and a task-suitability probability threshold. Automatic mode admits only model/reasoning pairs with at least the configured five to one hundred distinct cases, every attempt reviewed, sufficient empirical pass rate, acceptable p95 latency, and complete costs. When multiple candidates qualify, they must have identical case identities and repetition counts. An unreviewed answer is never a pass, failed, interrupted or exhausted turns cannot pass, and repeating a request does not create another distinct case.

[[src/lib/route-evidence.ts]] hashes graph behavior, selected source versions, node instructions, candidate task criteria/suitability threshold, review criteria, and other configured graph strategies. Evidence covers complete turns that can traverse different branches of that strategy; separate Model nodes keep separate evidence. Varying the evaluated model and reasoning pair or switching this node from evaluation to automatic retains its strategy identity. Changing context preparation, documents, instructions, graph configuration, or criteria requires fresh evidence. [[convex/routeEvaluations.ts]] stores owner-scoped thirty-day observations, capped at 256 per workspace and isolated by credential hash. Last-turn inspection in [[src/flow/route-evaluation-review.tsx]] saves criterion-level evidence-backed reviews and shows empirical quality, latency and full-turn cost. These are measurements on the chosen sample, not calibrated predictions or a production quality guarantee.

[[server/model-planner.ts]] first validates eligibility before paid context work for this model, then estimates UTF-8 input bytes divided by four after context preparation. The final forecast adds the candidate's measured mean complete-route overhead, the newly quoted generation cost times its measured attempt count, and the current automatic routing assessment cost, then divides by its reviewed pass rate. Overhead includes embedding, reranking, decisions, summaries, adequacy, upstream/downstream generation, repeats, and backups. Every attempted call must have usable reported usage and pricing; unknown cost excludes the candidate. Each pair must use an effort supported by its model; measured mean generation output (including provider-counted reasoning) supplies pair-specific output forecasts when available, otherwise the configured output forecast is labelled as an estimate; expected output must fit the node maximum. Expected reuse still controls cache-write forecasts and is reported separately from complete-turn evidence.

Unavailable server keys and unknown prices exclude a candidate. Custom rates apply only to the configured model that owns them; other candidates use the dated published catalog in [[src/lib/model-pricing.ts]]. No viable candidate produces an error eligible for the node's one explicit backup attempt. No implicit retry or alternate candidate call is made. The stream, usage ledger, planning inspection and canvas footer retain the selected model and reasoning effort; provider-cache identity distinguishes both. A separate planning record reports estimates and context-preparation cost so far; actual charges remain API-token-based ledger estimates.

[[server/task-router.ts]] evaluates suitability for every eligible pair in one batched Jev Noul call after context preparation, using the same rendered instructions, examples, selected Start values, history, documents and reached results as generation. Unselected sources stay excluded. Suitability is a provider assessment, not measured accuracy. Below-threshold pairs are excluded; missing, malformed or failed assessments stop selection rather than guessing another route. The call is reserved in the checkpoint before paid work and retained under the routing ledger purpose, including unknown usage on failure. Each reached node attempt reassesses the current task, including explicit repeats and backups; completed stages are reused through recovery.

The planner owns both context-price comparison and final candidate selection. It estimates the shared rendered input once per quote batch and returns the chosen target, its exact quote, and the planning trace together. [[server/model-preparation.ts]] coordinates eligibility, preparation using only eligible candidates, and final quotation of effective instructions/context, then chooses the lowest projected cost per passing answer among task-suitable reviewed pairs. Pair-specific evidence includes all evaluation-route calls; automatic routing adds a separately reported paid classification call whose usage is included in the final turn ledger, preparation total, and final complete-route forecast. Missing classification cost stops automatic generation rather than treating that call as free. Evaluation quality/latency evidence describes the configured sample, not a calibrated per-request prediction or a guarantee of automatic-route latency. The scheduler loads one evidence snapshot per reached automatic node and reuses it across preparation, final quotation, and repeats. Execution never searches the trace to recover a selected candidate or applies the previous model's rate overrides to a different provider. [[server/provider-ledger.ts]] owns preparation-cost totals; [[server/node-context.ts]] applies the same model-price policy while choosing representations.

## Provider cache

Cache planning uses content identity and reported usage, without claiming guaranteed provider hits.

The reusable prefix contains System instructions, configured examples, and selected documents. Provider model and reasoning participate in its hash; current query, selected Start values, history, and stage results remain outside this planned prefix. Changed prefix content or reasoning invalidates its evidence. API-reported cached reads (and OpenAI cache writes) establish evidence for a matching prefix. A reported miss clears it. Prefix observations expire after 30 minutes for OpenAI and five minutes for Gemini, and are capped at 128 per session.

For OpenAI, automatic routing explicitly controls prompt cache behavior using the installed direct SDK's Responses options and text breakpoints in [[server/model-prompt.ts]] and [[server/api.ts]]. Prefixes below the estimated 1,024-token threshold are not credited. A cold prefix is written only when its write premium plus projected later reads costs less than uncached requests. A single request remains uncached; a matching observed prefix can be reused. Projection assumes later reuse and is not a promise. Manual model mode retains ordinary provider defaults.

Gemini uses its implicit cache; no explicit cache object or paid storage is created. A cold prefix receives no assumed discount. A prefix above the estimated 4,096-token threshold can receive a projected discount only after reported cache reads for the same model/settings/content. Five-minute evidence is a conservative local heuristic, not a provider TTL guarantee. Actual provider hits or misses are always recorded independently of the forecast. See the official [OpenAI cache guide](https://developers.openai.com/api/docs/guides/prompt-caching) and [Gemini cache guide](https://ai.google.dev/gemini-api/docs/generate-content/caching).

## Optimization storage

The server retains bounded optimization records per conversation and account; Convex additionally stores reusable summaries.

[[server/session-memory.ts]] owns the bounded in-process pool, scoped by the persisted conversation ID plus a SHA-256 hash of server credentials. Each of sixteen sessions retains at most 256 summaries and 500,000 summary characters, sixteen pending generations, and 128 prefix observations, with a 30-minute inactivity TTL. The application API requires an authenticated Convex conversation and persistence connection. API tests execute the same required run lifecycle against the Convex test backend; there is no alternate session-ID or database-free API path.

An optional typed SummaryStore capability retrieves or stores completed summaries in [[convex/summaries.ts]] through [[server/convex-persistence.ts]]. Workspace ownership, credential hash, source content/version, exact query, and effective node task prevent cross-owner or stale reuse. Persistent summaries expire after 30 days and are capped at 256 per workspace; hourly cleanup drains expired entries in batches. Failed retrieval/generation/persistence retains full source rather than using an unconfirmed summary. Simultaneous calls within one server session share a pending promise; separate server processes can independently generate the same summary.

Reload and server restart retain durable summary reuse, but provider-cache evidence remains bounded server memory. Realtime database synchronization never establishes provider-cache validity. Persistent summaries are compression artifacts, not semantic retrieval or long-term customer memory.

## Settings and observation

Node settings opt into automation; inspection explains the chosen provider and context.

[[src/flow/model-routing-fields.tsx]] exposes evaluation/automatic mode, answer criteria, sample/quality/latency limits, checked model/effort rows with Use for task criteria and minimum suitability, expected output, and reuse count. [[src/flow/context-policy-fields.tsx]] exposes automatic context, adequacy probability, and optional preparation payback; automatic document bindings use the same checked rows as Start variables. [[src/flow/model-plan-details.tsx]] shows candidate exclusions, estimated costs, cache mode, and preparation costs in run inspection. Settings save or cancel together with the node and persist with graph configuration; plans and measurements are retained with completed turns.

## Preparation payback

The optional economic policy checks savings before summary generation or adequacy assessment. It preserves full selected sources when the cold forecast is too expensive or generation pricing is unknown.

[[server/automatic-context.ts]] quotes a cold summary call for each source longer than 1,600 characters, including the 1,600-token output ceiling, plus the batch Jev usefulness/adequacy packet. [[server/context-providers.ts]] owns the same provider instructions and packet construction used by this forecast. Optimistic savings compare the full optional context with removing all optional context through the cache-aware generation planner. Preparation proceeds only when these savings cover the forecast times the configured return ratio. This estimate assumes cold summaries, even when a durable artifact might exist; it deliberately may miss an opportunity rather than claim an unmeasured saving. Actual summary reuse and charges remain in the ledger.

If full optional sources exceed the final character budget, preparation can proceed despite the payback result so that adequate compression has a chance to preserve information. Mandatory query, selected Start fields, instructions and examples remain mandatory. Retrieval is explicitly configured and runs before this check; the policy does not disable retrieval. A validated preparation trace records the decision, cold estimate and optimistic savings. Failed or uncertain assessments retain full sources subject to the final optional budget, and cancellation propagates.

Frozen evaluation inputs and authenticated candidate replay are described in [[persistence]]. Strategy identity includes [[src/lib/evaluation-version.ts]] versions as well as graph and source configuration, so review, execution or installed provider-SDK changes invalidate earlier evidence. The [[evaluation]] harness reports confidence against labelled correctness and complete-route cost per passing case without changing runtime thresholds.

## Criterion reviews

Owner reviews cite recorded evidence for each configured criterion. An insufficient-evidence result cannot approve automatic routing.

[[src/lib/quality-review.ts]] treats each nonempty criteria line as one ordered criterion, up to twenty. Reviews retain pass, fail, or insufficient-evidence verdicts, reasons, and exact supporting quotes tied to frozen inputs, documents, stage outputs, call records, or captured transport bodies. [[convex/routeEvaluations.ts]] validates every reference against the owned stored artifact before atomically saving reviewer identity, time and the derived route grade. Stale concurrent edits are rejected. Failed execution cannot pass; incomplete artifact coverage or an unknown criterion leaves a successful route ineligible. A handoff can meet the answer criteria while its task outcome stays handoff rather than resolved. Positive, negative or mixed user reaction requires a later recorded user message; silence remains unknown.

[[src/flow/quality-review-form.tsx]] loads canonical artifacts through [[src/lib/run-artifact-load.ts]]. [[src/flow/quality-review-editor.tsx]] owns local review edits and provenance validation; [[src/flow/quality-review-fields.tsx]] reuses evidence and outcome controls. [[src/flow/route-evaluation-review.tsx]] retains selection of earlier answers and the complete-route quality, latency and cost report. The server derives eligibility from the reviewed criteria and execution evidence rather than accepting a caller-supplied boolean.
