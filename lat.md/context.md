# Context

Each reached Jev or Model builds its own context from identifiable conversation messages, reached stage outputs, and declared reference documents. The latest query, selected Start variables, and configured instructions remain mandatory. See [[routing]], [[canvas]], and [[chat]].

## Selection and representations

Explicit bindings select optional context before any provider call.

[src/flow/context-documents-editor.tsx](../src/flow/context-documents-editor.tsx) edits declared documents in the Start sheet using flat fields and InputGroup text controls. Each document's options menu owns removal; inputs have no adjacent removal button or explanatory descriptions. [src/flow/context-policy-fields.tsx](../src/flow/context-policy-fields.tsx) composes the node settings. [src/flow/context-document-binding-fields.tsx](../src/flow/context-document-binding-fields.tsx) owns representation selection, and [src/flow/context-relevance-fields.tsx](../src/flow/context-relevance-fields.tsx) owns optional relevance and its rates. Each control updates only its owned policy field. Binding lookup uses indexed source IDs for both editing and server selection.

[src/lib/context.ts](../src/lib/context.ts) owns documents, node context policies, selection traces, and document override validation. Start declares reference documents with stable IDs, names, full text, and optional supplied summaries. API clients may replace a declared document by ID; replacement never inherits an old summary. Documents are limited to 20 and 240,000 combined characters. A node selects each document as full text or a supplied summary; omission is the default. In manual mode without retrieval, missing selected summaries reject the request. Automatic context and retrieval use the original source regardless of an existing full/summary binding. Documents remain explicitly bound; automation never reads an unselected source.

[server/context.ts](../server/context.ts) applies the shared policy for both providers and Jev. The default is six previous messages, all reached upstream stage results, no documents, and a 24,000-character optional-context budget. Nodes can choose zero to 29 previous messages, all/selected/no upstream stages, and a 1,000–120,000-character budget. The budget counts chunk content, excluding prompt framing, the current query, selected Start values, system instructions, and example messages; it is not a token or monetary budget. Whole upstream results and documents take priority, followed by newest history. Oversized chunks are omitted rather than cut in half. Retained history keeps its chronological order.

Output chunks identify the producing node, logical source stage, and revision. A backup produces a result for the original stage, so selected stage bindings still work after failover. Joins and repeats use the latest revision for each logical stage. A chunk can only use an output already available on the reached path; bindings do not execute an unreached source. [server/upstream-context.ts](../server/upstream-context.ts) serializes retained outputs, including structured Jev decisions, without another truncation layer. [server/model-prompt.ts](../server/model-prompt.ts) puts retained documents in a stable, labelled data message after configured examples and before conversation history. Current-query data and stage results stay in the final user message. This preserves a reusable prefix without moving System instructions into the query.

## Relevance and observation

Optional Jev relevance filtering makes an additional batched evaluation of selected chunks.

[[server/context-providers.ts]] sends the current query, node task, and bounded candidate chunks to one TypeSafe call with one Noul question per chunk. Manual relevance and automatic assessment share the provider transport and answer mapping, while retaining their own questions and deadlines. The node supplies relevance instructions and a minimum omission probability, defaulting to 90%. Only confidently irrelevant chunks are omitted. Uncertain, missing, malformed, or failed results retain the selected context and record the reason. Cancellation stops execution. Relevance screening is not an authorization policy, and its selected chunk bodies are sent to Jev even when the downstream model ultimately omits them.

Every generation or decision attempt records a context trace linked to its call ID. It reports source IDs, representations, character counts, inclusion reasons, and any relevance probabilities. Included excerpts are limited to 600 characters per chunk and 4,000 characters per attempt; omitted bodies are not copied into the trace. The node inspector exposes these traces and clearly marks shortened excerpts. Completed traces persist with run results, while context settings and documents persist with the graph. See [[persistence]].

## Automatic context

Optional automatic selection chooses omit, short summary, detailed summary, or full text for each bound source on the reached path. It includes relevance screening and is mutually exclusive with the separate manual relevance option.

[[server/automatic-context.ts]] owns representation selection. Sources longer than 1,600 characters receive query-aware short (600 characters maximum) and detailed (2,400 maximum) summaries from GPT-6 Luna with None reasoning through [[server/context-providers.ts]]. The summarizer receives the current query and effective node task, including activated instructions and selected Start values. It focuses on relevant evidence while preserving source language, numbers, constraints, exceptions, negation, uncertainty, and attribution. Summary generation has no implicit retries, a 30-second deadline, and at most two concurrent sources per node. A batched Jev evaluation compares each variant against the original source for the current query and node task. Only confident irrelevance permits omission; only adequate variants above the configured probability can replace full text. Missing, malformed, failed, or uncertain assessments retain the full source. Cancellation propagates. This screening reduces risk; it does not prove factual equivalence or answer quality.

[[server/node-context.ts]] prepares each reached node with its selected variables, context bindings, optional price projection, and accounted providers. Effective instructions are a required result of node preparation, while [[server/context.ts]] owns only source materialization and selection. Optimization returns representation choices and the preparation decision together, without mutating a caller through callbacks. Summary generation and adequacy assessment are supplied as one paired capability; a partial pair cannot be configured. [[server/provider-ledger.ts]] records these calls through the same budget and usage path as classification and answer generation. The graph scheduler receives the prepared context and its trace.

Bound source bodies are limited to 120,000 characters before assessment, then selected representations are subject to the node's final optional-context budget. Whole oversized chunks can still be omitted for budget; mandatory query, System instructions, examples, and selected Start values are retained. History and stage-result summaries change the actual downstream text while preserving message roles and stage identity. Compression itself does not extend the recent history window or execute sources outside declared bindings and reached lineage. Retrieval separately selects passages from explicitly enabled saved history and bound documents.

Without price routing, selection prefers the shortest adequate representation. With price routing, it greedily compares each adequate replacement using the total model/cache projection described in [[optimization]]; an observed cached full source can remain cheaper than a new summary. The comparison is not a global combinatorial optimum. Preparation is paid upfront and recorded separately, so the first turn can cost more than manual full context. The trace exposes the chosen representation, probability, summary creation/reuse/unavailability, and any budget omission.

[[server/session-memory.ts]] reuses summaries by source-content SHA-256, source kind, summarizer version, exact query, and effective node task. Changed queries or activated instructions cannot reuse a summary prepared for another task. Changed source text never inherits an older summary. Within a session, simultaneous callers share one pending generation and only its producer records the provider cost. The current summary identity excludes artifacts prepared under the earlier completion policy. Summaries require a normal SDK `stop` finish reason and validated structured output. Truncated, filtered, invalid, or cancelled generations do not populate the cache; their failures retain full selected source subject to the final budget, and their reported model and usage stay in the ledger. The in-process cache expires after 30 minutes; owner/workspace/content/credential-scoped Convex summaries can be reused for 30 days, including after a server restart. These summaries do not extend the available history window. See [[persistence]].

## Passage retrieval

Reached nodes can retrieve passages from selected documents and explicitly enabled saved history before compression and budgeting. Retrieval does not resume an earlier graph execution.

[[src/lib/retrieval.ts]] owns passage, selection, policy, and trace schemas. [[server/retrieval.ts]] splits explicitly selected original sources into exact overlapping slices of at most 2,400 characters with approximately 200 characters of overlap, retaining source IDs, labels, and character offsets. Each source is limited to eighty passages, and selections above 512 passages reject before embedding. Sources are indexed lazily, in batches of sixteen across source boundaries. One turn shares pending indexing work; source content, label, kind, embedding model, dimensions, version, workspace, and credential scope determine persistent identity.

[[server/retrieval-providers.ts]] embeds through the direct OpenAI AI SDK provider using text-embedding-3-small at 512 dimensions, with no retries and a thirty-second provider deadline. Its SDK middleware captures reported usage before embedding-count validation, so invalid results still account for paid work. Missing usage stays unknown rather than propagating the SDK’s `NaN` sentinel. [[convex/retrieval.ts]] combines native vector and text search with reciprocal-rank fusion. It returns 4–32 candidate passages, default sixteen. Native search filters isolate selected document versions and the current conversation; hydration additionally admits only the selected source keys. Vector search considers at most 64 hits and text search at most the candidate limit per collection, so retrieval is bounded approximate search rather than exhaustive recall. Missing or failed indexing and search are explicit errors.

Jev grades all candidates in one Score evaluation, with four levels from irrelevant through directly necessary evidence, and a fifteen-second deadline. Only a complete set of confident grades permits reordering and removal of passages whose scores round to the irrelevant level zero. Missing, uncertain, malformed, or failed grades preserve hybrid-search ordering and record the outcome. Cancellation propagates. The configured passage limit is 1–16, default six, and confidence defaults to 90%. Selected passages still undergo optional relevance/compression and the final budget; the trace separately distinguishes retrieval selection from final context inclusion.

Saved history retrieval is disabled by default and explicitly selects up to 200 prior messages from the same conversation, within a 120,000-character source cap. It excludes the active user/assistant pair and labels partial failed replies. Recent message context remains separately configured. No document outside a node's bindings is embedded, assessed, or retrieved. Model prompts frame retrieved passages as source evidence and explicitly mark a retrieval result without retained evidence. Run inspection shows candidates, grades, offsets, confidence, history limits, and reranking failures; [[persistence]] owns the index lifecycle.

## Conditional instructions

Each node can append up to eight instructions from selected typed Start values or accepted reached Jev outputs. Rules resolve per turn and do not establish persistent customer state.

[[src/lib/conditional-instructions.ts]] owns the rule schema. [[server/conditional-instructions.ts]] resolves ordered rules against selected values and reached logical stage outputs before retrieval and compression. Uncertain, failed, exhausted, unreached, unselected, and mismatched decisions do not activate a rule. Latest logical stage revisions determine activation. [[src/lib/routing.ts]] validates field types, variable selection, output identity, upstream bindings, and forward reachability, including the primary logical stage of a backup. Effective instructions reach both Jev questions and model prompts and participate in summary and provider-prefix identity. Traces record activation without copying instruction bodies.

[src/flow/context-retrieval-fields.tsx](../src/flow/context-retrieval-fields.tsx) and [src/flow/conditional-instructions-fields.tsx](../src/flow/conditional-instructions-fields.tsx) compose existing flat node settings. Text uses shared InputGroup controls, removal belongs in each item's options menu, and no additional modal or Apply step is introduced. Removing a selected input, source node, or Jev output prunes its dependent rules. [[src/lib/context.ts]] owns shared binding cleanup. Settings save with the existing node editor and persist with graph configuration.

## Preparation economics

Automatic context can require projected savings to cover cold preparation costs before summary or adequacy calls.

Full selected sources are retained when savings do not justify preparation or prices are unknown; sources over budget can still be prepared. [[optimization]] documents the forecast, source isolation, and recorded preparation decisions in [[src/lib/context.ts]].
